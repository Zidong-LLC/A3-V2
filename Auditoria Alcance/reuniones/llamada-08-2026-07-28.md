## 8. Jerarquía clave: pedido → órdenes de servicio → análisis

```
Pedido
  └── contiene una o varias órdenes de servicio
        └── cada orden contiene uno o varios análisis/perfiles/pruebas
```

- Una veterinaria puede enviar varias órdenes en una sola recogida.
- Cada orden corresponde normalmente a un paciente.
- Cada paciente/orden puede tener múltiples análisis.
- **El pedido agrupa todas las órdenes y es lo que luego se factura/paga.**
- A3 lo explica con la lógica de supermercado/domicilio: una factura puede contener varios productos; aquí el pedido contiene varias órdenes.

## 9. Varias órdenes en una misma recogida
- El bot no debe cerrar el pago después de la primera orden si el cliente puede agregar más órdenes.
- Después de cerrar una orden, debe preguntar: "¿Deseas agregar otra orden de servicio o continuar con el pago?"
- Si agrega otra orden, mantiene la misma veterinaria/cliente.
- La nueva orden puede tener otro médico solicitante, otro paciente, otra especie y otros análisis.
- Ejemplo de segunda orden: médico Cristian Vargas, paciente Nene, canino, raza Pinscher, macho, análisis 207 / perfil cachorro 7.

## 10. Diferencia entre agregar análisis y agregar orden
- Dentro de una orden: preguntar si quiere agregar otro análisis.
- Después de cerrar la orden: preguntar si quiere agregar otra orden de servicio.
- No confundir "otro análisis" con "otra orden".
- A3 remarca que la pregunta debe decir "otra orden", no "otro análisis", cuando ya se cerró una orden.

## 11. Resumen de la orden
- El resumen de cada orden está bien en estructura.
- Debe mostrar los datos de la orden/paciente: veterinaria, dirección, médico, paciente, propietario, análisis, observaciones si aplica.
- **No debe incluir forma de pago dentro del resumen de cada orden.**
- Motivo: la forma de pago corresponde al pedido/factura total, no a cada orden individual.

## 12. Forma de pago: ubicación correcta en el flujo
- **Decisión clave: la forma de pago debe preguntarse al final del pedido, no dentro de cada orden de servicio.**
- El pedido puede contener 1, 2, 3 o más órdenes.
- Cuando el usuario termine de agregar órdenes, ahí sí se pregunta cómo pagará el total.
- Forma lógica del flujo:
  1. seleccionar cliente/veterinaria;
  2. crear orden de servicio 1;
  3. agregar análisis a esa orden;
  4. cerrar/resumir orden;
  5. preguntar si desea agregar otra orden;
  6. repetir si corresponde;
  7. cerrar pedido;
  8. mostrar total;
  9. preguntar forma de pago;
  10. pasar a facturación/Alegra.
- A3 insiste en que preguntar pago por cada orden puede confundir al cliente.

## 13. Facturación: se factura el pedido, no cada orden por separado
- Aclaración acordada: A3 no quiere facturar cada orden de servicio por separado en este flujo.
- **Se factura el pedido completo, que puede contener varias órdenes.**
- La factura debe incluir los ítems/servicios correspondientes a esas órdenes.
- Jorge resume el punto: no se facturan órdenes de servicio aisladas, se factura el pedido cuando ya terminó.
- Sergio aclara que en facturación electrónica ambas formas existen, pero para A3 el requerimiento es que varias órdenes puedan ir en la misma factura/pedido.

## 14. Pago, Alegra y cobro

- La pasarela o sistema contratado será quien cobre.
- La plataforma/chatbot debe capturar o preparar la información necesaria para pasarla a facturación.
- **A3 menciona que quieren usar Wompi/Bancolombia para pago en línea.**
