# Checklist — Llamada 2

**Fecha:** 22 de abril de 2026
**Proyecto:** A3 Laboratorios / chatbot + plataforma interna
**Estado general:** revisión de feedback del bot, ajustes de flujo, pagos, programación de rutas, mensajeros y lógica de plataforma.

## 1. Objetivo de la llamada
- Reinicializar / revisar el bot para validar feedback y modificaciones enviadas por A3.
- Revisar un caso real: un cliente programó ruta, la conversación quedó derivada al mensajero, luego la doctora envió soporte de pago y el laboratorio ya no veía esa conversación porque estaba del lado del mensajero.
- Aclarar cómo manejar cuando un cliente pide dos cosas en una misma conversación (gestión de pago + programación de ruta).

## 2. Problema detectado: conversación derivada al mensajero
- **El sistema actual genera pérdida de visibilidad para recepción/laboratorio.** Cuando la conversación queda asignada al mensajero, recepción deja de ver qué pasa después.
- El cliente quiere evitar que la conversación quede "encerrada" solo en el mensajero.
- Se plantea la necesidad de doble visibilidad o doble asignación.
- Luciano advierte que una doble conversación simultánea puede ser confusa para el cliente.
- **Criterio acordado:** primero cerrar o cambiar de etapa un proceso, y luego seguir con el siguiente.

## 3. Comportamiento esperado cuando se programa una ruta
- El bot primero debe verificar si el cliente está registrado, contrastar contra la base y confirmar que quien solicita corresponde al cliente correcto.
- Si el cliente existe, confirma dirección. Si la dirección no corresponde, permite modificarla.
- **Cuando se asigna mensajero, la conversación no debe cerrarse completamente.** El chat pasa a otra fase/estado, pero el agente puede seguir respondiendo dudas mientras por detrás se notifica al mensajero.
- La asignación del mensajero debe ser un proceso interno, no una conversación directa visible para el cliente.
- El estado del cliente/pedido debe cambiar internamente: "asignar motorizado", "motorizado asignado", "notificando al motorista".

## 4. Conversaciones inactivas o resueltas por llamada
- Problema: algunas gestiones se resuelven por teléfono, pero el chat queda abierto.
- **Pedido:** después de cierto tiempo o al cerrar manualmente, la conversación debería volver a un estado inactivo/disponible para nuevas solicitudes.
- Solución propuesta: el agente humano tendrá acceso a la plataforma para cambiar la etapa de la conversación cuando el caso se resolvió por llamada.
- Pendiente: definir estados operativos del chat — "en gestión humana"; "resuelto por llamada"; "inactivo"; "disponible para nueva solicitud"; "programación de ruta activa".

## 5. Consulta de resultados
- La consulta de resultados, por ahora, dará respuesta genérica. Para una respuesta real hay que conectar con ANAR/Anarvet en otra fase.
- Datos mínimos que debe pedir el bot: nombre del paciente; nombre del veterinario; nombre de la veterinaria o doctor.
- Estado: flujo básico en esta fase; integración real para fase posterior.

## 6. Gestión de pagos
- **Cambiar el nombre de "aclara tus pagos" a "gestión de pagos".**
- **El bot debe permitir adjuntar soporte de pago** (PDF, imagen u otro archivo).
- El bot debe confirmar recepción del soporte: *"Hemos recibido tu pago / soporte, será procesado"*.
- **El soporte debe subirse a la plataforma** para esperar aprobación o revisión.
- Si el usuario no quiere adjuntar pago y tiene dudas, derivar a persona de pagos.
- Responsable de validación: área de pagos / contabilidad / administrativo, no el bot.

## 7. PQR
- PQR se maneja con un link: el flujo básicamente deriva a un enlace/formulario.
- Pendiente: integrar el link correcto en el bot.

## 8. Cliente nuevo
- Si el usuario dice "soy cliente nuevo", no debe seguir el flujo de búsqueda normal.
- **El bot debe derivar directamente a atención al cliente.**
- Área responsable: atención al cliente / recepción.
- En plataforma: debe crearse una notificación tipo *"se te ha asignado una solicitud de cliente nuevo"*.
- Una vez derivado, el proceso del bot se cierra para ese caso.

## 9. Búsqueda por NIT / NIF / nombre fiscal
- El bot debe encontrar clientes por NIT/NIF o nombre fiscal.
- **Debe funcionar con dígito de verificación y sin dígito de verificación.**
- Si busca por NIT y no encuentra, pedir nombre.
- Si busca por nombre y no encuentra, no volver a pedir el mismo dato.
- Si no encuentra por ninguno, derivar a servicio/atención al cliente.
- **Evitar bucles repetitivos.**

## 10. Validación de documentos de cliente nuevo
- El formulario para cliente nuevo puede hacerse dentro del agente conversacional.
- **Los documentos, como RUT, deben subirse a una carpeta de Google Drive.**
- El cliente debe dar enlace y permisos de acceso a esa carpeta.
- **Debe intervenir una persona humana para validar documentos.** A3 aclara que han recibido documentos falsos.

## 11. Programación de ruta y asignación de mensajero
- Si el cliente existe, se confirma dirección y se programa ruta.
- Se preguntó si se podía asignar mensajero por GPS o cercanía.
- **Luciano aclara que geolocalización en tiempo real requeriría aplicación móvil.**
- Alternativa viable: guardar ubicación/dirección de veterinarias en la plataforma y enviar link de GPS al motorizado.
- Recepción debe mantener control de rutas; actualmente la asignación se hace en recepción y eso no cambiaría completamente.

## 12. Visibilidad para recepción
- Recepción debe ver qué rutas fueron asignadas.
- Recepción debe ver si el mensajero recibió la asignación.
- Recepción debe ver cuándo el mensajero marca una muestra como recogida.
- **La plataforma debe permitir que administradores vean todo el historial**, aunque las conversaciones estén derivadas al motorizado.

## 13. Reasignación de mensajero
- **Debe existir autoasignación por zona.**
- Recepción debe poder confirmar o cambiar la asignación **antes** de notificar al mensajero.
- Si recepción cambia el mensajero, se notifica al nuevo motorizado.
- Estado: aprobado conceptualmente.

## 14. Rol específico para mensajeros
- **Crear usuarios específicos para mensajeros.**
- Los mensajeros no deben ver toda la plataforma interna; deben ver una sección limitada con rutas/pedidos.
- Cada mensajero debe ver primero lo asignado a él, y también pendientes generales por recoger.
- **Cuando un mensajero recoja una muestra, debe marcarla como recogida.**
- Al marcarla como recogida, debe desaparecer de la lista de pendientes.

## 15. Orden de servicio / remisión
- Cuando se programe ruta, el bot debe avanzar hacia la remisión u orden de servicio.
- **El chat debe pedir los campos de la orden de servicio paso a paso**, no un formulario aparte.
- Campos mencionados: nombre del paciente; especie; edad; propietario; exámenes enviados; valor del examen/perfil.
- **Al finalizar la orden, debe aparecer opción de pago.**

## 16. Link de pago
- **El bot no debe generar directamente el link de pago por seguridad.**
- El pago debe redirigir a una página, plataforma o link predefinido.
- El link de pago depende del proveedor usado: PSE, PayU/Paya, Redeban, datáfono/plataforma externa, banco u otro operador.
- La generación/confirmación del pago requiere control humano o plataforma segura.

## 17. Formas de pago
- El cliente puede pagar de inmediato o contraentrega / contra recogida.
- **No usar la palabra "crédito" hacia el cliente.** Internamente algunos clientes pueden pagar después, pero no quieren comunicarlo como crédito.
- Medios mencionados: efectivo contraentrega; PSE; transferencia bancaria; posible link de pago según proveedor.
- Agregar nota de validación de pago: *"Estamos validando tu pago con el departamento administrativo/financiero"*.

## 18. Regla crítica: siempre programar ruta
- **Aunque el pago no esté validado, la ruta debe programarse igual.** A3 lo deja claro: pague o no pague, se tiene que programar la ruta.
- No dejar al motorizado esperando por validación de pago.
- La validación de pago queda en administración/contabilidad.

## Resumen final — Llamada 2

Se trabajó sobre casos reales que aparecieron al probar el flujo. El principal problema fue que,
al derivar una conversación al mensajero, recepción perdía visibilidad y podían quedar mensajes
importantes sin revisar, como soportes de pago. Se acordó que la plataforma debe permitir
visibilidad administrativa completa, roles específicos para mensajeros, seguimiento de rutas,
check de muestra recogida y control desde recepción. También se ajustó el flujo de cliente nuevo:
si alguien dice que es nuevo, el bot no debe intentar validarlo como cliente existente, sino
derivarlo directamente a atención al cliente. Además, se definió el nuevo enfoque de "gestión de
pagos", permitiendo adjuntar soportes, pero dejando la validación del pago en manos del área
administrativa. La regla operativa más importante fue que **la ruta siempre debe programarse,
aunque el pago todavía no esté validado**.
